# 采价台演示与面试手册

本手册只引用当前 v3 冻结评测和合成浏览器闭环。它证明本地风险控制、结果复算与故障恢复，不代表真实企业上线、未知版式准确率或显著效率提升。

## 演示准备

```powershell
uv sync --all-groups
Set-Location web
npm ci
npm run build
Set-Location ..
uv run python scripts/generate_procurement_demo.py --output output/procurement-demo-v3
uv run agentharness --workspace . --data-dir output/procurement-demo-run-v3 --port 8741
```

核心演示使用 `华东优包报价单.xlsx`、`沪上包装报价单.pdf` 和 `星河包装报价单.pdf`。采购目标必须明确“白色 PE 快递袋、250×350 mm、60 微米、单色印刷、15 天、开票”；星河包装的供应商名需要人工复核。

## 5 分钟演示

| 时间 | 操作 | 可核对证据 |
|---|---|---|
| 0:00-0:40 | 描述采购目标并一次提交三份报价。 | 页面关联 `session_id`、`purchase_request_id`、`run_id`；原件按 SHA-256 存储。 |
| 0:40-1:25 | 等待 Agent 结构化需求并执行组合分析。 | `procurement_capture_requirement` 一次进入后端流水线；星河包装供应商名 55%，Run 进入 `require_human`。 |
| 1:25-2:00 | 在报价复核面板把供应商名改为“星河包装”，再点击“开始比价”。 | 只有人工 correction API 能写报价事实；原值、来源、actor 和时间均保留。`/analyze` 从同一 Run 恢复。 |
| 2:00-3:00 | 查看供应商比价。 | `procurement_execute_analysis` 内部完成解析、身份匹配、历史、Decimal 比价、复算和选择项；每个阶段有业务审计。 |
| 3:00-4:00 | 核对快照并正式选定华东优包。 | Approval 绑定 `snapshot_id + input_sha256 + quote_id`，只允许 `allow_once` 后写入决定。 |
| 4:00-5:00 | 打开审批报告和运行审计，刷新或重启服务。 | 报告含原件哈希、人工修正、规则版本、Checkpoint、Verification、Approval、Token 与证据指纹。 |

无字段复核的直接闭环固定为一个 Run、3 个模型回合；上述含一次人工复核的公开场景是一个 Run、5 个模型回合、3 次工具调用。审批工具成功后由运行时验证确定性终态输出，不再为复述已提交的决定额外调用模型。模型负责需求理解和受治理编排，确定性后端负责采购计算。

## 故障恢复

| 场景 | 系统行为 | 验证点 |
|---|---|---|
| 字段缺失或低置信度 | 保存 `require_human` Checkpoint，阻止比价。 | 结构化人工修正后 `/analyze` 复用原 `run_id`。 |
| 报价新增或修正 | 原子清除当前快照引用，拒绝旧审批。 | 旧 `snapshot_id` 返回冲突；重新分析产生新版本和新哈希。 |
| Provider 超时或 429 | 按预算重试，429 优先遵守 `Retry-After`。 | 事件和 `usage.provider_attempts` 保存尝试，不依赖上游控制台。 |
| HTTP 取消 | 取消传播到内部审批任务。 | 响应失败后不会继续提交采购决定。 |
| 进程中断 | Run 租约恢复为可解释状态，采购事实与 Artifact 保留。 | 重启后任务、Checkpoint、审批和报告一致。 |
| 数据库中途失败 | 创建与正式决定分别使用单个 SQLite 事务。 | 不留下孤立 draft、部分决定或缺审计的业务状态。 |

## 当前证据

- 冻结集：31 份合成报价、6 种版式、22 类异常；原始字段抽取 617/620（99.52%）。
- 辅助链：物料身份与规格匹配 31/31、金额 31/31、硬约束漏检 0/17、不合格错误入选 0。
- 人工门控：2 个待复核字段；未复核仍可进入排序的报价从基线 2 份降为 0。
- 浏览器闭环：1 个 Run、3 次工具、1 次一次性审批、5 个模型回合、212 Token、Fake Provider 费用 0；控制台 0 错误/0 警告。
- 原始指标、三张截图和中文审批报告见 [`docs/evidence/`](evidence/README.md)，可用 `evaluate_procurement.py verify` 独立复算。

当前 v3 没有可复用的真人对照和真实模型公开证据，因此不要写“显著提效”“真实企业上线”“真实模型总体准确率”或历史模型费用。

## 面试追问

**为什么需要 Agent，而不是纯固定工作流？** 采购计算是固定规则，但自然语言需求、缺口说明、何时调用分析和最终解释存在不确定性。Agent 处理这些环节；后端流水线处理事实、金额、资格和排序。

**如何防止模型改报价或算错钱？** 模型工具集中没有报价修正入口。报价只能由带 actor 的结构化人工 API 校正；单位、税率、币种、运费、MOQ、交期、材质、颜色、印刷、预算和有效期全部由 Decimal 与硬规则计算并复算。

**为什么组合成一个分析工具？** 解析、匹配、历史、比价和复算是确定性依赖链。让模型逐步调度会增加 Token、失败点和越序风险；组合工具减少模型回合，但内部阶段事件和审计仍完整保留。

**Checkpoint 为什么不是简单重跑？** 同一 `run_id` 保存消息、工具结果和待恢复状态。人工复核后只继续下一阶段，避免重复导入、重复计费或重复审批。

**为什么审批会失效？** Approval 绑定当前快照、规范输入哈希和报价 ID。任何需求或报价变化都会改变输入哈希，因此旧审批不再代表当前事实。

**评测最容易被质疑什么？** 数据为合成、版式有限，低置信度字段使用真值回放完成离线门控验证；它不证明未知供应商文档或真实业务提效。公开证据明确隔离这些边界。
